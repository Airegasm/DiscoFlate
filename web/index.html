About DiscoFlate
A self-hosted Discord bot + local control panel that turns chat commands into timed smart-plug fires, driving an inflation-themed capacity game. Everything runs on your own device and controls your own smart plugs on your own network — no cloud middleman. It's a real bot account (not a self-bot), so it stays within Discord's rules.

What it does

  • Capacity engine — capacity accumulates while the active pump runs, at a rate set by that device's seconds-to-100% calibration.
  • Per-range everything — dice (Ndsides), a luck modifier, per-command cooldowns (per-user or shared), custom commands with per-person use budgets, ongoing announce text, one-time milestone messages + images.
  • Custom commands — build fire / roll / say commands in the UI; add them to whichever ranges they should be active in.
  • Max-roll prizes — hitting a perfect roll N times unlocks limited-use bonus commands, range-gated or global, with a cumulative counter.
  • End sequences — let capacity run past 100% to a final burst threshold with its own entry milestone and final message/image.
  • Timed events, modes, leaderboard, per-user cooldowns, anti-spam buffer, and multi-server support with anonymized cross-server echoes.
  • Snapshot — capture a webcam frame and post it to the channel.
  • Operator Controls — dashboard buttons (Roll, Stop, Pump, Broadcast Capacity/Users) that fire real in-channel actions as the owner, exactly as if they'd typed the command.
  • Mock mode — run the whole game with no hardware at all; set the virtual pump's calibration on the Devices tab.
Messages are fully templated via [placeholders] — [capacity], [capacity_bar], [dice], [result], [secs2capacity], [timer], [commands], [custom_commands], [cmd_remain], [operator], and more (see Placeholders & examples below).
⚠️ Physical devices are involved. The app forces the active device off on shutdown (and on Android when torn down), but always keep a physical power switch as a backstop. Built for consenting adult roleplay.

Custom commands — how to set them up
A custom command is a chat trigger you invent (e.g. !spin). You build it once on the Commands tab, then switch it on for the capacity ranges where it should work.

The command types

  • fire — turns the device on for a fixed number of Seconds. (Drives capacity if the device is a pump.) Add + Add Device Fire rows to also fire other devices, each for its own seconds, independently.
  • roll — rolls dice and fires for the total. Leave Dice/Sides on rng to use the current range's dice, or pin specific dice (e.g. 2 d 6).
  • say — text-only reply, no device. Good for lore, hints, or status.
  • chance — a gamble. Rolls 1–100 against your Chance %; Luck % is a ± chance to force the outcome (positive = force a win, negative = force a miss). A win posts the Success message and fires the 🟢 win device rows; a miss posts the Failure message and fires the separate 🔴 failure device rows (leave them empty to fire nothing on a miss). Placeholders [roll], [chance], [luck], [secs] work in both. Like every command it's range-gated, cooldownable, and exhaustable (Max/person, set per range).
  • game-pushluck — a private button minigame: the player presses 💨 Pump for points at a rising bust chance (starts at Bust start %, +% / pump) or 🏦 Bank to lock in. Bust = 0. You set max pumps + points/pump and the outcome tiers (score → broadcast message + optional pump fire credited to the player).
  • game-simon — a private memory minigame: the bot shows a growing emoji sequence for Reveal (s), hides it, and the player repeats it with buttons. Score = rounds survived. Set # symbols + max rounds and the same outcome tiers.
  • game-balloon (Don't Pop It) — a button grid; reveal safe cells for points, or 🏦 Cash Out before you hit a hidden balloon (pop = 0). Set # cells, # balloons, points/cell. Score = points cashed out.
  • game-rps — Rock-Paper-Scissors vs the bot, first to Rounds to win. Score = rounds you won.
  • game-slots — a public one-pull slot machine (no Play button): running the command spins 3 reels in-channel. Score = 3 (three of a kind), 1 (a pair), 0 (no match). Set # symbols (more = rarer wins).
  • game-blackjack — ephemeral 21 vs the dealer: Hit / Stand. Score = 0 bust/lose · 1 push · 2 win · 3 natural blackjack.
  • Most games post a public ▶ Play button locked to whoever ran the command; play is private (ephemeral) until the tiered result broadcasts (slots is the exception — it's fully public). Every result is labelled with the game and respects cross-server anonymity (real name only where the player is a member). Placeholders [score], [luck], [secs] work in tier messages.
  • Luck modifier — a flat ± added to the final score before the tier is picked (positive = luckier, negative = harsher). Set it per range (in that range's command table) or on the game's Always-On entry. If a game is in both a range and Always-On, the range's luck wins; leave the range luck blank to fall back to the Always-On value.

Per-command options

  • Device — (active pump) or a specific device you've added.
  • owner-only — only the Owner can use it. reply pings user — the reply @-mentions the caller. hide from command list — keep it out of [commands].
  • react only (non-game) — instead of posting a text reply, the bot adds a reaction (the emoji box, default 💨) to the caller's message. The fire/roll/credit still happen — only the reply text is suppressed — so rapid-fire commands stop flooding the channel. Cross-server echo is skipped (a reaction is local to the origin channel); falls back to a normal reply if the emoji can't be added.
  • Description — shown next to the command in [commands]. Reply — the templated message it posts (see Placeholders below).
  • Starts events — comma-separated names of (off-by-default) timed events this command switches on temporarily. They revert on Session reset / app restart.
  • Row icons — every command / event / range row has 📋 Duplicate (a clash-safe copy, e.g. fill → fill-copy), 💾 Save as template (stashes it in the Templates tab for reuse), ✏️ Edit (expand/collapse), and ✕ Delete. In the Templates tab, ＋ Add to Config ports a saved template back in (auto-renaming on a clash).
⚠️ Two-step setup — this trips people up: creating a command does nothing on its own. A command only works in a range after you add it to that range (Game → Capacity ranges → open a range → “+ Add command to this range”). Its cooldown, max uses/person, and scope are set there, per range — not on the command itself.
Example — a !spin roll command: Commands tab → + Add command → Name spin, Type roll, Dice/Sides left on rng, Reply 🌀 [user] spun [dice] = [result] → +[secs2capacity]%. Save. Then Game → Capacity ranges → open the 66–100% range → + Add command to this range → !spin, and set Max/person 3, Cooldown 30, Scope per-user. Now !spin is live only in the top band.

Capacity ranges — how to set them up
Ranges are capacity bands (From % → To %) that change the game as the meter climbs. They're evaluated top-down — the first band that contains the current capacity wins. Edit them in Game → Capacity ranges.
⚡ Always-On commands (the collapsible at the top of the ranges section) is the exception to per-range membership: any custom command listed there works in every range while the toggle is on — handy for utility commands like !cointoss. Each entry has its own cooldown and max/person (blank = default / unlimited); minigame entries also get a luck modifier. If a game is Always-On and a member of a range, the range's cooldown, max, and luck take precedence there.

Each range holds

  • Dice + Luck — the built-in 🎲 roll for this band (e.g. 1 d 4 low, 2 d 6 high). Luck is a ± % nudge on the result.
  • Announce — ongoing text shown with roll/capacity while you're in the band. Milestone + Image — posted once the moment capacity enters the band.
  • The command table — the 🎲 dice roll (always present) plus every custom command you've added to this range. Per command, per range: Max/person (blank = unlimited; [cmd_remain] then reads “unlimited”; a value set in an earlier band carries forward), Cooldown (blank = the default), and Scope (per-user = each person waits their own cooldown; per-command = one shared cooldown for everyone). Minigame commands also expose a Luck cell here — a flat ± on the score for this band, which overrides any Always-On luck.
  • Range Start Command — one command auto-fired once when the band is entered.
  • Event actions on entry — Enable/Disable named timed events as the band is entered.

End & End Sequence

+ Add End Sequence = a buildup band with a final threshold; reaching it posts a final message/image, then ends & resets the session. + Add End = just that terminal threshold, no buildup. Capacity may tick above 100% up to the End threshold. Only one End / End Sequence is allowed, and nothing comes after it.
Example: three bands — 0–33% rolls 1 d 4, 33–66% rolls 1 d 6, 66–100% rolls 2 d 6 with a Milestone “🎉 Two-thirds full!”. Add !spin to the 66–100% band only. Then + Add End Sequence at 120% with a final message “💥 Full burst!” — capacity can climb past 100% until it hits 120% and the session ends.

Timed events — how to set them up
Events are automatic actions on a timer — no one has to type anything. Build them on the Events tab. They only run while Activation is on; turning Activation off cancels every event and clears cooldowns.

Two timing modes

  • loop — fires every N seconds, repeatedly. Set max to stop after that many repeats (blank = forever). In the message, [current_loop], [total_loops] (∞ if uncapped), [loop_timer] (the interval), and [next_round] (a “Next Round in N seconds” line that's blank on the final round) are available.
  • once — fires a single time, N seconds after Activation turns on (re-arms on the next off→on).

Five actions

  • message — post its text to the announce channel.
  • fire — run a device for N seconds.
  • roll — auto-roll a device (its own dice/sides, or the current range's).
  • capacity — add or set the meter by a value.
  • chance — each fire is a gamble (like the chance command): rolls vs chance % (± luck); a win fires the 🟢 win rows + posts the success message, a miss fires the 🔴 failure rows + posts the failure message.
Every action can also post a message, and placeholders work everywhere. Events are OFF by default — turn one on three ways: tick it here, list its name in a command's Starts events, or have a range Enable it on entry.

Activation, cooldown & messages

  • When a !command's Starts events tries to turn an event on, it's smart: if it's already running it posts the global “in process” message; if it's still on cooldown it posts the global “cooldown” message; otherwise it activates and posts that event's own activation message.
  • Each event has its own cooldown (seconds) that starts when it finishes (a “once” fires, or a loop hits its max), and an optional end message posted at that point.
  • The two “in process” / “cooldown” messages are global (set at the bottom of the Events tab) and support [event] and (cooldown) [cooldown].
  • Trigger First Loop Immediately fires the first round the instant it's activated instead of waiting one interval.
  • Clean up previous round (loops only) — each new round deletes the previous round's message so a long loop doesn't spam the channel; only the current round is visible. The End message, if set, replaces the last round and stays. Great for things like PumpRoulette. (These are the bot's own messages, so no extra permission is needed to delete them.)
  • When an event is started by a !command, its pump fires credit that person's leaderboard (session + lifetime). Events turned on by the checkbox or a range aren't attributed to anyone, so they credit no one (they still drive capacity + the pump timer).
Example — a slow drip only in the top band: Events tab → + Add event → Name drip, mode loop, every 45 s, action fire, 2 seconds on the active pump, message 💧 a slow drip…. Leave it OFF. Then Game → Capacity ranges → the 66–100% band → + Add event (on entry) → drip / Enable. Now the drip only runs once the meter is two-thirds full, and stops when it drops back out.

Set up your private Discord bot
A 2-minute, one-time setup. There's no verification or app review — that only applies to bots in 100+ servers. Each person runs their own bot with their own token; never share a token.
  1. Open the Discord Developer Portal → New Application → give it a name (e.g. your bot's name) → Create.
  2. Left sidebar → Installation. Set Install Link to None — this removes the public add-to-server link. Do this first: Discord won't let you change the gateway intents (next steps) until Install Link is None. In that same tab, under Installation Contexts, make sure Guild Install is checked (User Install can stay off) — without it you'll get "Installation type not supported" when you try to add the bot to a server.
  3. Left sidebar → Bot, turn Public Bot OFF — now only you can invite it. This is what makes it a private bot.
  4. Still on the Bot page, under Privileged Gateway Intents, turn Message Content Intent ON (required so it can read commands) and Save.
  5. Get the token: on that same Bot page, in the Token section click Reset Token (Discord keeps the token hidden, so this reveals a fresh one) → Copy it immediately — it's only shown once. Keep it secret; it's your bot's password. You'll paste it into DiscoFlate's Discord tab shortly. (Lost it? Just Reset Token again — that makes a new one.)
  6. Left sidebar → OAuth2 → URL Generator. Tick scope bot; under permissions tick Send Messages (and Attach Files if you'll use images/snapshots). Copy the generated URL at the bottom, open it, and add the bot to your server.
  7. Back here → Discord tab → paste the token → Save & connect → pick the server and channel to listen on.
  8. Flip Activation on (top-right) and test from the Dashboard → Controls.
If it connects but doesn't respond to commands, re-check that Message Content Intent is on and that you picked the right channel.

Adding your bot to someone else's server

Because it's private, only you can add it — you can't hand a friend a link. Two ways to get it into a server you don't own:
  • Stay private (cleanest): have that server's owner give you the Manage Server permission there, then open your own invite link (step 6) and pick their server — as the app owner it works even while private. Remove the permission afterward if you like.
  • Temporarily go public: Portal → Bot → turn Public Bot ON, and Installation → set Install Link to Discord Provided Link. Now anyone with Manage Server there can add it with the link. Once it's in, switch Public Bot back OFF and Install Link back to None to re-lock it.
Either way it's harmless to be in another server — your bot only fires your devices and only listens in the channel you select; elsewhere it just sits idle.

Set up Tuya / Geeni / Smart Life plugs
Tuya-based plugs (incl. Geeni and anything in the Smart Life app) are controlled through Tuya's cloud API. The credentials come from Tuya's developer platform — not your Geeni/Smart Life app login. Tuya labels them with slashed double names, which is why they look unfamiliar: Access ID / Client ID and Access Secret / Client Secret.
  1. Go to platform.tuya.com ↗ and create a free developer account (separate from your plug app's login).
  2. Cloud → Development → Create Cloud Project. Pick the data center matching where your app account lives — US (Americas) for Geeni and most US plugs. It must match the Data center dropdown in Devices → Brand credentials, or every call fails with an auth error.
  3. The project's Overview tab shows Access ID/Client ID and Access Secret/Client Secret — paste those two into DiscoFlate → Devices → Tuya / Geeni credentials.
  4. Enable the IoT Core service on the project (Service API → free trial subscription). Without it, device calls fail even though the credentials are right.
  5. In the project: Devices → Link App Account → scan the QR with your app. ⚠️ Geeni gotcha: the QR link works with the Smart Life or Tuya apps, but usually not Geeni's own app. If your Geeni account won't link, re-pair the plugs into the Smart Life app (same hardware, same protocol) and link that.
  6. Your plugs now appear in the project's device list — each shows a Device ID. That's what goes in the device_id field when you add the plug in DiscoFlate → Devices. Select it as the active pump and Calibrate.
If a call fails after setup: check the data center matches the project, the IoT Core trial hasn't expired, and the device is linked into this project (not just visible in the phone app).

Set up ESPHome (for Kauf plugs)
Kauf plugs run ESPHome firmware with a built-in local web interface — that's what DiscoFlate talks to (no cloud, no account). Most stock Kauf plugs have it enabled out of the box.
  1. Get the plug on your Wi-Fi: on first power-up it broadcasts a setup hotspot (Kauf Plug XXXX) — connect to it, or use Kauf's captive-portal, and join it to your network.
  2. Find its IP address — check your router's device list, or try the hostname (e.g. http://kauf-plug.local).
  3. Confirm the web server is on: open http://<plug-ip> in a browser. If you see a page listing switches/sensors, you're good. If the browser says the connection was refused, the plug has no web server running — the ESPHome web_server: component is off by default. Add it to the plug's ESPHome config and re-flash, then retry. (A "connection refused" in DiscoFlate's Activity log means the same thing.)
  4. Note the switch id from that page — it's usually relay (DiscoFlate's default). If yours is named differently, remember it.
  5. In DiscoFlate → Devices → Brand = Kauf → enter the plug's host (its IP) and, if it isn't relay, the entity (switch id). Click Add.
  6. Select it as the active pump (radio) and Calibrate it (run it, tap Full when done) so capacity tracks.
  7. Only if you enabled web-server auth on the plug: fill the Kauf credentials (web username/password) in the collapsible section above the device list.
If the plug won't respond, open http://<plug-ip> directly and try toggling the switch there — that confirms the web server is reachable and gives you the exact switch id.

Troubleshooting

"Connection refused" / plug won't respond
Connection refused (in the Activity log, or in a browser at http://<plug-ip>) means nothing is serving HTTP at that address+port — it's not a wrong switch id (that gives a 404) and not the plug being offline (that times out). The plug answered and said "no listener here." Work through these in order:
  1. Right IP? Confirm 192.168.x.x is actually the plug (router device list / http://kauf-plug.local). A refusal from the wrong device looks identical.
  2. Different port? Some builds put the web server on :8080. Try http://<plug-ip>:8080 in a browser — if that loads, just enter <plug-ip>:8080 as the host in Devices. No re-flash needed.
  3. No web server at all? If neither port loads, the ESPHome web_server: component isn't running (it's off by default in ESPHome). Add it to the plug's config and re-flash — see "Where is the ESPHome YAML?" below.
Add this to the device's YAML, then Install/flash (OTA — no USB needed since it's already on ESPHome):
web_server:
  port: 80
Where is the ESPHome YAML?
Depends on how the plug was set up:
  1. Home Assistant + the ESPHome add-on (most common) — files live on the HA host at /config/esphome/<device-name>.yaml. Easiest: ESPHome dashboard → the device's card → EDIT. Or open the file via the File editor / Samba / SSH add-on. Shared secrets are in /config/esphome/secrets.yaml.
  2. Standalone ESPHome (Docker, or pip install esphome on a PC) — the .yaml files sit in whatever directory you run esphome from, typically ~/esphome/ or a mounted config/ dir. One <name>.yaml per device plus a shared secrets.yaml.
  3. Flashed from the web installer (web.esphome.io) with no dashboard — there's no persistent YAML file; config only exists at flash time. Re-create it in a dashboard (option 1 or 2) to change anything.
Kauf plugs specifically: Kauf ships adoptable stock firmware. In the ESPHome dashboard the plug appears via mDNS with an ADOPT / TAKE CONTROL button — adopting it generates a small local <name>.yaml in /config/esphome/ that references Kauf's published package (github.com/KaufHA). That generated file is where you add web_server:, then Install.
Flashing / enabling web_server (web & OTA)
If the plug is already on ESPHome and your Wi-Fi (it is, if you set it up before), you almost never need a USB cable — do it over the air. USB web-flashing is a last resort, and a Kauf mains plug has no external USB port, so it means opening the case.

Route 1 — OTA via the standalone ESPHome dashboard (no cable)

Set up the dashboard (either one runs as a local web app in your browser):
pip (Python 3.9+; a venv is cleanest):
pip install esphome
esphome dashboard config/
Serves the dashboard at http://localhost:6052, storing each device's YAML in config/. Or Docker (same LAN as the plug):
docker run --rm --net=host -v "$PWD/config:/config" -it ghcr.io/esphome/esphome
Then flash it OTA:
  1. Open http://localhost:6052. The plug appears under Discovered (via mDNS) since it's already on ESPHome + your Wi-Fi.
  2. Click ADOPT / TAKE CONTROL → name it → the dashboard writes config/<name>.yaml (referencing Kauf's package).
  3. Open that device's ⋮ → Edit (or edit config/<name>.yaml) and add web_server: { port: 80 } (as two lines).
  4. Save → Install → Wirelessly (OTA). It compiles and pushes over Wi-Fi — no cable. (First compile downloads the toolchain and is slow; later ones are quick.)
  5. After the plug reboots, http://<plug-ip> loads → add it in DiscoFlate → Devices.
⚠️ Run the dashboard on the same network as the plug or mDNS/OTA won't reach it. Kauf stock firmware may prompt for an OTA password during install — default documented on github.com/KaufHA.

Route 2 — USB web-flash via web.esphome.io (only if OTA is impossible)

Needs a Chromium browser (Chrome/Edge — WebSerial isn't in Firefox/Safari), a 3.3 V USB-to-UART adapter, and access to the ESP's pads. ⚠️ A Kauf mains plug has no external USB — you must open the case and wire an adapter with the plug unplugged from mains. Advanced; use Route 1 if you're not comfortable.
  1. Plug unplugged from mains. Open it; wire USB-UART: TX↔RX, RX↔TX, GND↔GND, 3V3↔3V3. Pull GPIO0 low / hold the button to enter flash mode.
  2. Open https://web.esphome.io in Chrome/Edge → Connect → pick the serial port.
  3. Either Prepare for first use (installs base ESPHome, then adopt it in the dashboard and add web_server: as in Route 1), or Install a .bin you exported from the dashboard that already includes web_server.
Kauf shortcut: Kauf ships a browser-based installer (ESP Web Tools) and their latest stock firmware already has web_server enabled. Flashing current Kauf firmware — via their web updater or OTA — re-enables it without hand-editing YAML. See kaufha.com / github.com/KaufHA for current steps.

Formatting

Press Enter for a new line. Discord markdown works: **bold**, *italic*, `code`. A literal \n also becomes a newline.

Readability — Display output headers

When several people fire commands and multi-stage minigames at once, the lines braid together. Turn on Display output headers (Game → Limits & announcements, at the top) and every command / minigame / event message is prefixed with a **[label · user]** tag, so each line is traceable to who and what it belongs to. The user portion respects cross-server anonymity — servers where the actor isn't a member see ANON instead of the name.
Turn on Rich status embeds (same spot) to post the capacity check, both leaderboards, the auto-report, and custom Broadcasts as bordered embed cards instead of plain text — the border and color stripe make those status blocks stand apart from rapid command chatter. Per-command replies stay plain (use react only or Display output headers for those).

Minigames — how each one plays
Minigames are custom command types (Commands tab → Type → game-*). Running one posts a public ▶ Play button locked to whoever typed it; the game itself is ephemeral (only the player sees it), and when it ends the tiered result broadcasts to the channel — with any pump fires credited to the player's leaderboard. Slots is the exception: it plays fully in-channel with no Play button. Every game maps its final score through your Outcome tiers (score → message + optional device fires), so YOU decide what a win pays. A per-range or Always-On Luck value is a flat ± added to the score before the tier is picked.

💨 Push Your Luck (game-pushluck)

Press-your-luck banking. Each 💨 Pump adds Points/pump to a pot — but the bust chance starts at Bust start % and climbs +% / pump with every press. 🏦 Bank locks the pot in as the score; busting scores 0. Hitting Max pumps auto-banks. Score = points banked. Tune it greedy (low start, steep step) or generous (high ceiling, shallow step).

🧠 Simon (game-simon)

Memory. The bot shows a growing emoji sequence for Reveal (s) seconds, hides it, and the player repeats it with buttons. Each cleared round adds one symbol. One wrong press ends the game. Score = rounds fully cleared; clearing Max rounds is a perfect run. Fewer Symbols (2–6) and a longer reveal = easier.

🎈 Don't Pop It (game-balloon)

Minesweeper-style nerve test. A grid of Cells hides Balloons; revealing a safe cell adds Points/cell, and 🏦 Cash Out keeps the total. Revealing a balloon pops — score 0. Clearing every safe cell scores the whole board. Score = points held at the end. More balloons per cell = spicier.

✊✋✌️ Rock Paper Scissors (game-rps)

Best-of series vs the bot — first to Rounds to win takes the match, ties replay. Score = rounds the player won (win or lose the match), so tiers can pay partial credit for a close loss or reserve the top tier for a sweep.

🎰 Slots (game-slots)

One public pull — the reels spin right in the channel. Score is fixed: 3 = three of a kind, 1 = any pair, 0 = no match. Symbols (2–8) sets the odds: more symbols = rarer wins (with 6 symbols a triple is 1-in-36, a pair about 42%). Tiers at ≥3 / ≥1 / ≥0 map jackpot / small win / nothing.

🃏 Blackjack (game-blackjack)

Classic 21 vs the dealer, infinite deck, Hit / Stand, dealer stands on 17. Score is fixed: 0 = bust or dealer wins · 1 = push (including blackjack-vs-blackjack) · 2 = win · 3 = natural blackjack on the deal. No knobs beyond the tiers — the game IS the odds.
Shared rules: a game charges its cooldown + per-person use when the command runs (not when Play is pressed); one use = one game. Abandoned games pay nothing. A session pause cancels live games and refunds the use. Results are labelled with the game's name and respect cross-server anonymity. Placeholders [score], [luck], [secs], [secs2capacity], [game] work in tier messages, and games can trigger Starts events on completion.
