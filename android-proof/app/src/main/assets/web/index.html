System commands

Custom commands
A command = its gates + an action block run in order when it's typed: fire (fixed seconds or until a %), roll (blank dice = the range's dice & luck), chance (a gamble with nested win/miss blocks), message (how the bot replies — put it after the rows that produce [secs]/[result]), award, command_gate, and more. The minigame types post a ▶ Play button; the player plays privately and the final score → tier broadcasts (tiers can fire, run actions, even count toward a Perfect Prize). A command works once it's in a range (Game → Capacity ranges) or in ⚡ Always-On — range values (cooldown, fire seconds/device, dice, luck) always override the command's own. See the Help tab for placeholders.

Capacity ranges
⚡ Always-On commands
Use for utility commands (like !cointoss) that should always be available. Each entry sets its own cooldown / max per person (blank = default / unlimited). A command lives here OR in ranges, never both — adding it to a range moves it out automatically, and range-bound commands don't show in the picker.
Announce shows with roll/capacity while in the range · Milestone/Image post once on reaching it. ⚙ Per-command settings sets each command's dice (roll), enabled toggle, cooldown & scope, a Range Start Command, and event actions on entry.
🏁 End Sequence = a range with a final threshold; reaching it posts a final message then ends & resets the session (no activation-off message). End = just that terminal threshold, no buildup. Capacity may tick above 100% up to the End threshold. Only one End / End Sequence is allowed, and nothing comes after it.

📈 Capacity events
One-shot triggers that fire the moment capacity reaches a threshold (1–999%; above 100% only happens inside an End Sequence's buildup). They operate independently of ranges — while one runs, its restrictions take precedence over normal ranges — but the End / End Sequence overrules them: nothing triggers after the end fires, and the session end cancels any running capacity event. One-shot per session (re-armed by Session reset / Activation).
During the event = while its action block is running (actions execute in order; use wait to shape timing). Gate play with a command_gate row: a Resume row at the block's end lifts it when the event completes; leave it off and the gate persists for the session. Gates apply to chat commands only — dashboard controls still work; an Allow row wins over everything, including range membership.

⏱ Timed events
These two are global: posted when a !command tries to activate an event that's already running or still on cooldown.
An event is three action blocks: 🚀 On activation (once, when a command starts it) → 🔁 Each round → 🏁 When it ends. Events are OFF by default — tick one to run, or have a custom command start it temporarily. loop runs a round every N seconds (set max to stop after that many; blank = forever); once runs a single round N seconds after arming. Loop placeholders: [current_loop] [total_loops] [loop_timer] [next_round]. Runs only while Activation is on; turning Activation off cancels all events and clears cooldowns. Rounds never overlap — a slow block (wait/poll) just delays the next round.

🗳 Polls
People vote with !agvote 1, /vote, or the embed's buttons — one vote per person, no take-backs.
A poll is an action: reference it from a command (type poll), a timed event (action poll), a capacity event's block, or even a winning option of another poll. It posts as a rich embed — Poll: <title> with the body and numbered options — runs for its duration (optionally reposting every N seconds), then the winning option's actions execute. Ties break at random; with no votes the Fallback option wins (none marked = nothing happens). One poll at a time. A poll inside an event's action block keeps that event running until the poll completes, then the event's remaining actions resolve.

Broadcasts
Preset messages you can fire from the Chat tab → Controls (“Broadcast Custom”). Placeholders work ([capacity], [operator], …). Posted to your channel as the owner.

🎮 Minigames
A minigame is a named profile: a game, its settings, its luck, and the outcome tiers that run when the score lands. Play one from any command with a minigame action row — so a command can fire a pump and post a message before the game, and carry on after it. Two profiles of the same game can differ completely, and any number of commands can call either.

🏁 Competitions
A competition is an action (start it from any action block). Fully button-driven: players press Enter Challenge on the embed and roll privately — the rolls you define below, in order (complete them all to qualify). Results post all at once; highest score wins by the Win by metric. Winner / no-winner outcomes are action blocks — e.g. an embed message row, fire [winner_score], award a bonus command, or command_gate everyone else. Race & raffle are being redesigned and will return. Placeholders: [winner] [winner_score] [runnerup] [total_score] [results].

🤝 Bonus Rounds
A Bonus Round is a teamwork cash-in, started by a bonus_round action. First bank amounts with an award action (volume secs/%) (pump seconds or capacity %, on [winner]/[range_leader]/[session_leader]/…). The round posts an embed with a Confirm button for bonus holders; once the needed holders confirm (all, or just the top holder) before the timer, your action block runs with the pooled [total_bonus_secs] / [total_bonus_pct] — then the banks are spent. Use fire [total_bonus_secs] or add % [total_bonus_pct] to apply them.
🏆 Rewards
Achievement rewards: N perfects unlock an action block for the earner (an award row grants a bonus command — target [user]). A perfect roll (any roll action hitting its maximum) bumps the roll counter automatically; an achievement action row (e.g. on a blackjack 21 tier) bumps any counter you name. Progress is per person, resets on unlock (re-earnable) and on Session reset. Progress placeholders: [count] [goal] [remaining] [counter] [prize].

Custom commands — how to set them up
A custom command is a chat trigger you invent (e.g. !spin). It's simply its gates (ranges, cooldowns, owner-only, …) plus an action block — an ordered list of action rows that run when it's typed. The bot only speaks through message rows, so “the reply” is just the message row you put after the rows that do things (their results flow on as placeholders).

The action rows

  • message — plain text or an embed (titlebar + body); optionally carries a button gated to winner / runner-up / range leader / session leader / top bonus holder / everyone / an allowlist, which runs a nested block when pressed (with freeze + deadline/fallback).
  • fire — pump a fixed number of seconds, OR until capacity adds/reaches a %, on the active pump or a specific device; can block others while pumping and run Post-Pump Actions. Publishes [secs] [secs2capacity] [timer] for later rows. Fires credit the runner.
  • roll — roll dice and fire the total as seconds. Blank Dice/Sides = the current range's dice & luck; its own NdN + Luck are the fallback (range values win). Publishes [dice] [result] [secs]. A maximum-total roll is a perfect — it advances Perfect Prizes.
  • chance — a gamble: rolls 1–100 vs Chance % (Luck % = ± chance to force the outcome), then runs the nested 🟢 win or 🔴 miss block. [roll] [chance] [won] flow to the rows after.
  • award — grant a target ([user] = the runner, [winner], a name…) a bonus command with N charges (stashable / progression-locking / deadlined), or bank a volume (seconds / %) for a Bonus Round. Publishes [target] [bonus_cmd] [charges] [amount].
  • command_gate — stack Block / Allow / Resume rows over commands (all, one, this range's, always-on) or events (one, all timed, all capacity). Persist until resumed or session reset.
  • notify — put a line on the scene's notify overlay from inside any block. An event ROUND or a minigame tier never goes through a command, so this is the only way it can announce itself on the stream — e.g. [user] added [secs]s to [device] · Roulette [current_loop]/[total_loops].
  • …plus broadcast (a saved preset) · command (run another command) · capacity add/set · wait · start a poll / competition / bonus_round · achievement (bump a Perfect-Prize counter) · stop_devices (kill any running pump) · end_session. Rows run in order; 📋 duplicates one, ⋮⋮ drags to reorder.
  • game-pushluck — a private button minigame: the player presses 💨 Pump for points at a rising bust chance (starts at Bust start %, +% / pump) or 🏦 Bank to lock in. Bust = 0. You set max pumps + points/pump and the outcome tiers (score → broadcast message + optional pump fire credited to the player).
  • game-simon — a private memory minigame: the bot shows a growing emoji sequence for Reveal (s), hides it, and the player repeats it with buttons. Score = rounds survived. Set # symbols + max rounds and the same outcome tiers.
  • game-balloon (Don't Pop It) — a button grid; reveal safe cells for points, or 🏦 Cash Out before you hit a hidden balloon (pop = 0). Set # cells, # balloons, points/cell. Score = points cashed out.
  • game-rps — Rock-Paper-Scissors vs the bot, first to Rounds to win. Score = rounds you won.
  • game-slots — a public one-pull slot machine (no Play button): running the command spins 3 reels in-channel. Score = 3 (three of a kind), 1 (a pair), 0 (no match). Set # symbols (more = rarer wins).
  • game-blackjack — ephemeral 21 vs the dealer: Hit / Stand. Score = 0 bust/lose · 1 push · 2 win · 3 natural blackjack.
  • Most games post a public ▶ Play button locked to whoever ran the command; play is private (ephemeral) until the winning tier's block announces the outcome (slots is the exception — it's fully public). A tier is just score op N + an action block — its message rows ARE the result announcement ([score] [game] [user] work), fire rows credit the player, and it can award or bump an achievement toward a Perfect Prize (“3 blackjacks → bonus command”).
  • Minigame luck — a flat ± added to the final score before the tier is picked. Set it per range (in that range's command table) for range-bound games, or on the game's Always-On entry for always-on ones.

Per-command options

  • owner-only — only the Owner can type it (still callable by the bot internally). hide from command list — keep it out of [commands].
  • react to acknowledge (non-game) — the bot adds a reaction (default 💨) to the caller's message; great for rapid-fire commands. The block still runs — its message rows still post.
  • Range gate — an EXTRA capacity band on top of range membership; useful for granted bonus commands.
  • Description — shown next to the command in [commands].
  • Starts events — comma-separated names of (off-by-default) timed events this command switches on temporarily. They revert on Session reset / app restart.
  • 🎮 Minigames are profiles, not command types. A minigame is a named profile on the Triggers tab — a game, its settings, its luck and its outcome tiers. Any command plays one with a minigame action row, so the command can fire a pump and post a message before the game and carry on after it, with [score] [game] [secs] filled in. Only that one player's run waits — everyone else's commands, the timed events and the capacity loop carry on. Two profiles of the same game can differ completely, and any number of commands can call either.
  • 📣 Notify overlay (per command). One overlay serves every command. Design a Text overlay on the Scenes tab, then pick it in Scenes → 🖼 Session Overlays; each command's own line plays on it when the command runs. Tick 📣 notify overlay on a command and edit its text — [user] [mention] [command] and the usual placeholders all work, and the default is [user] just triggered [command]. A run that was blocked (paused, on cooldown, held by an intro, gated) never announces itself, and with no notify overlay picked it's a quiet no-op.
  • ⏸ Pause overlay. A scene group that covers the stream the moment you hit ⏸ Pause in the header, and clears on ▶ Resume. Pick it in Scenes → 🖼 Session Overlays. The shipped Pause group is a full-frame black card reading [operator] will be right back!, drawn above everything else.
  • Row icons — every command / event / range row has 📋 Duplicate (a clash-safe copy, e.g. fill → fill-copy), 💾 Save as template (stashes it in System → Templates for reuse), and ✕ Delete. To open or close a row, click its title strip — anywhere that isn't one of those buttons, a checkbox, a field or the ⋮⋮ drag handle. Click it again to close. In System → Templates, ＋ Add to Config ports a saved template back in (auto-renaming on a clash).
⚠️ Two-step setup — this trips people up: creating a command does nothing on its own. It only works after you either add it to a range (Game → Capacity ranges → open a range → “+ Add command to this range”) or put it in ⚡ Always-On — never both: a range-bound command leaves Always-On automatically. Per range you set its cooldown, max uses/person, scope, and (for fire commands) a Fire override — range values always beat the command's own, so one !pump can drive different pumps for different lengths in different bands.
Example — a !spin command: Triggers tab → Custom commands → + Add command → Name spin, then in its block add a roll row (Dice blank = the range's dice) and a message row 🌀 [user] spun [dice] = [result] → +[secs2capacity]%. Then Game → Capacity ranges → open the 66–100% range → + Add command to this range → !spin, and set Max/person 3, Cooldown 30, Scope per-user. Now !spin is live only in the top band.

Capacity ranges — how to set them up
Ranges are capacity bands (From % → To %) that change the game as the meter climbs. They're evaluated top-down — the first band that contains the current capacity wins. Edit them in Game → Capacity ranges.
⚡ Always-On commands (the collapsible at the top of the ranges section) is the alternative to per-range membership: a command listed there works in every range while the toggle is on — handy for utility commands like !cointoss. Each entry has its own cooldown and max/person (blank = default / unlimited); minigame entries also get a luck modifier. A command lives in ranges OR Always-On, never both — adding it to a range removes it from Always-On, and range-bound commands don't appear in the Always-On picker.

Each range holds

  • 🎲 Range dice + Luck — this band's dice (e.g. 1 d 4 low, 2 d 6 high) and a ± % luck nudge. Any roll action here uses them (they override the roll row's own NdN/luck).
  • Announce — ongoing text shown with roll/capacity while you're in the band. Milestone + Image — posted once the moment capacity enters the band.
  • The command table — every custom command you've added to this range. Per command, per range: Max/person (blank = unlimited; [cmd_remain] then reads “unlimited”; a value set in an earlier band carries forward), Cooldown (blank = the default), Scope (per-user = each person waits their own cooldown; per-command = one shared cooldown), a Fire override (seconds + device — beats the command's own fire row while in this band), and a minigame Luck cell (± on the score).
  • Range Start Command — one command auto-fired once when the band is entered.
  • Event actions on entry — Enable/Disable named timed events as the band is entered.

End & End Sequence

+ Add End Sequence = a buildup band with a final threshold; reaching it posts a final message/image, then ends & resets the session. + Add End = just that terminal threshold, no buildup. Capacity may tick above 100% up to the End threshold. Only one End / End Sequence is allowed, and nothing comes after it.
Example: three bands — 0–33% rolls 1 d 4, 33–66% rolls 1 d 6, 66–100% rolls 2 d 6 with a Milestone “🎉 Two-thirds full!”. Add !spin to the 66–100% band only. Then + Add End Sequence at 120% with a final message “💥 Full burst!” — capacity can climb past 100% until it hits 120% and the session ends.

Timed events — how to set them up
Events are automatic actions on a timer — no one has to type anything. Build them on the Events tab. They only run while Activation is on; turning Activation off cancels every event and clears cooldowns.

Two timing modes

  • loop — fires every N seconds, repeatedly. Set max to stop after that many repeats (blank = forever). In the message, [current_loop], [total_loops] (∞ if uncapped), [loop_timer] (the interval), and [next_round] (a “Next Round in N seconds” line that's blank on the final round) are available.
  • once — fires a single time, N seconds after Activation turns on (re-arms on the next off→on).

Three action blocks

  • 🚀 On activation — runs once, when a command's Starts events switches the event on, before round 1. (Events ticked on / enabled by a range skip this — nobody “activated” them.)
  • 🔁 Each round — the loop's payload: any action rows (message / fire / roll / chance / capacity / award / poll / competition / command_gate / …), run in order every interval. Loop placeholders [current_loop] [total_loops] [loop_timer] [next_round] work inside.
  • 🏁 When it ends — runs after the final round (a “once” fired, or a loop hit its max), detached from the event — e.g. message → wait 5m → fire. When the event ran a poll, each end action can be gated on which option won.
Events are OFF by default — turn one on three ways: tick it here, list its name in a command's Starts events, or have a range Enable it on entry. A slow round (a wait or poll inside) never stalls the game — the next round simply queues behind it.

Activation, cooldown & cleanup

  • When a !command's Starts events tries to turn an event on, it's smart: already running → the global “in process” message; on cooldown → the global “cooldown” message; otherwise it activates and runs the event's On activation block.
  • Each event has its own cooldown (seconds) that starts when it finishes.
  • Trigger First Loop Immediately runs round 1 the instant it's activated instead of waiting one interval.
  • Clean up previous round (loops only) — each round's messages replace the previous round's so a long loop doesn't spam the channel; the end block's first message replaces the last round and stays. Great for things like PumpRoulette.
  • When an event is started by a !command, its pump fires credit that person's leaderboard (session + lifetime). Events turned on by the checkbox or a range aren't attributed to anyone.
Example — a slow drip only in the top band: Triggers tab → ⏱ Timed events → + Add event → Name drip, mode loop, every 45 s; in Each round add a fire row (2 seconds) and a message row 💧 a slow drip…. Leave it OFF. Then Game → Capacity ranges → the 66–100% band → + Add event (on entry) → drip / Enable. Now the drip only runs once the meter is two-thirds full, and stops when it drops back out.

The canvas

Drag snaps to the 5% grid — hold Shift to place freely, or untick grid & snap below the canvas. On the canvas itself: drag to place, ◢ resize, ⟳ rotate. Coordinates are stored as fractions of the frame, so a design works at any resolution of the same aspect ratio.

The two lists

They sit to the right of the canvas: Add an overlay on top, the scene's contents below. Rows are the draw stack, front first: 👁 always-on vs callable — a callable one ghosts on the canvas rather than vanishing, so you can still place it · 🤫 hides it from the canvas only so you can reach whatever sits underneath; it is an editing aid and never touches the stream · ▲▼ front/back · ➦ move to another group · ⚙ options · − remove.

Scene groups

The contents list shows one group at a time — pick it in the dropdown, or All overlays. ➕✏️🗑 create, rename and delete them (deleting a group keeps its overlays, just untagged). Anything you add while a group is selected joins that group, and a group fires as a batch from a scene_group action.

The Scoped / 🌐 Global toggle: Scoped groups belong to this scene; Global groups are callable from every scene — same list, same canvas, same options, so a global overlay is designed exactly like any other. Globals are always callable (the camera only mounts the live scene's always-on overlays), and a global group fires alongside a scene group of the same name.

Overlay kinds

🖼 Media (image or video) · 🅣 Text with live placeholders · ⏳ Timer · 📊 Capacity Gauge · ⏱ Device Timers · ▬ Solid, a flat colour block, full-frame by default, for a backdrop behind a group with no image file needed · and the four self-gated cards — 🗳 Poll, 🏁 Competition, 🤝 Bonus Round, 📣 Broadcast — each of which draws only while its own round is running. A poll, a competition and a bonus round can never run at once, so all four cards can share one corner.

The media library

Every file lives in data/images, so 🔁 PC ↔ Android Config Sync and ⬇ Export Scene bundle them automatically. Limits: images 8MB, audio 24MB, video 96MB.

🎥 Video streams — getting started
DiscoFlate sends a virtual camera: your webcam with overlays composited into it. You pick that virtual camera in Discord instead of your real one, and everything you design on the Scenes tab plays inside your live call. Desktop only — Android can't register a camera device for Discord mobile, so the phone drives the PC instead (🖥 VC Remote).

First, the one-time driver

A virtual camera needs a system driver, and it cannot be bundled — on Linux it's a kernel module built against your running kernel, on Windows it's an admin-registered system filter. You only do this once.
  • Just press 🩺 Driver in the Chat tab's 🎥 section. It genuinely probes (it opens a device, it doesn't guess) and offers a one-click install when something's missing.
  • Windows — it installs OBS Studio via winget, purely because its installer registers the virtual-camera driver. You never have to run OBS; DiscoFlate does its own compositing. If the driver doesn't register, open OBS once, click Start Virtual Camera, close it.
  • Linux — it installs / loads v4l2loopback (sudo apt install v4l2loopback-dkms, then sudo modprobe v4l2loopback exclusive_caps=1 card_label="DiscoFlate Cam"). The button does both, with a password prompt. No OBS needed at all.
  • macOS — same as Windows: OBS installed once for its driver.

Then, every session, in this order

  1. Build a scene (Scenes tab) — or start from the shipped Your Scene. Whichever scene is selected here is the live one.
  2. Join the Discord voice/video channel and pick it in the Chat tab's Channel dropdown. The 🎥 section only appears for video channels.
  3. ▶ Start virtual cam. The preview shows exactly what viewers get — trust it over your own Discord tile, which Discord always mirrors.
  4. In Discord → voice & video settings → pick DiscoFlate Cam as your camera, then turn your camera on in the call. Nothing shows yet, and that's correct: the feed is black until you go LIVE. Get yourself set up in private.
  5. Flip LIVE (top-right). If Go Live is set to open with an intro, your intro stages play over black and hand over to the group you chose; otherwise the picture comes up straight away.

Worth knowing

  • The camera holds your webcam while it runs. Anything else wanting that same device will find it busy.
  • Black is deliberate. Not LIVE = a genuinely black frame with no overlays at all, so you can start the camera, pick it in Discord and get ready without anyone seeing the room. During an intro it stays black with just the intro playing on it (untick black during intro in Go Live Options to show the camera behind it instead).
  • 🪞 Mirror flips the camera image only, before overlays are drawn — use it if your camera hands you a reversed picture, or something in shot reads backwards. It does not fix your own Discord tile, and cannot: Discord mirrors your self-view and offers no way to turn that off, so your overlays read backwards to you there whatever this is set to. It has no effect at all on STARTING SOON or an intro — those frames are blanked before anything is drawn, so there is no camera image left to flip. The preview above is the finished frame exactly as sent; judge your layout there, not in your own tile.
  • 🔍 Detect lists the sizes each attached camera really supports, portrait modes included.
  • ⏸ Pause covers the stream with your pause overlay and stops the pumps; ▶ Resume clears it.
  • Audio overlays play on this machine's speakers, not down the video pipe. To get them to viewers, route your system audio into Discord (a loopback / monitor source).
  • On a phone, the 🎥 section becomes 🖥 VC Remote: video runs on the PC and the phone drives it. Needs Remote access on at the PC, with the phone's IP whitelisted.

💬 The Chat tab — owner cockpit
A live mirror of any watched channel (pick it top-left — voice channels show a 🔊 and unlock the 🎥 video section). Run a whole session from here without touching Discord.
  • Plain text posts AS YOU — your Owner name + Discord avatar, via a webhook the bot manages. Without the Manage Webhooks permission it falls back to a Owner:-prefixed bot post (the status line under the send box tells you which mode you're in).
  • !command executes as the Owner — cooldown-exempt, owner-only commands allowed, reply lands in that channel. Enter sends. To speak in your own voice from a command, use a message row set to As: the OWNER.
  • Custom Buttons — one-click launchers managed via 🔧. A button runs a !command, and that command's action block does the rest — fire a pump, play an overlay or a scene group, start a poll, run a whole sequence. ＋ new makes a fresh owner-only, hidden command for a button. They belong to the scene, so switching scenes swaps the whole button set with it.
  • Video channels — on desktop your feed shows above the chat: the live virtual-cam output (overlays included — exactly what viewers see), and 🔍 Detect probes each attached camera for the sizes it really supports, portrait modes included. On the phone the video section becomes 🖥 VC Remote: video calls run on your PC, and Connect links the app straight into the PC's panel (same Chat tab, buttons and camera controls, driving the PC) — enable Remote access + whitelist the phone's IP on the PC first; the phone's back button returns to the local app.
  • The virtual camera is desktop-only. Android has no way for an app to register a fake camera — that needs a system driver (root) — and Discord mobile only ever lists the real front/back cameras. On desktop, run DiscoFlate on the PC you join the call from and pick the virtual cam in Discord desktop's video settings.
  • Overlays live on the PC. The virtual camera is the camera home base — design scenes on the Scenes tab and they play into your Discord call from the PC. (A phone-hosted view exists at /stage for screen-share setups, but it's parked and not linked from the UI.)
  • Listen / Announce tickboxes (Discord tab, on each channel) — two independent jobs, both on by default. Listen takes commands typed there; Announce posts events, milestones, auto-reports and pause/resume there. Untick Listen for a spectator or announcements channel that shows the show but ignores commands; untick Announce to keep a busy channel quiet while commands still work; untick both to mute it completely without forgetting it. Persistent and per channel, and it composes with Isolate.
  • Isolate (next to the channel picker) — while ticked, every broadcast (events, milestones, auto-reports, timers, cross-server echoes, owner-voice posts) goes only to the channel selected here, across every server. Announce-ticked channels are suppressed too while pinned, so nothing leaks into another server. The bot keeps listening everywhere — commands typed in other channels still run and reply there — and if the pinned channel isn't live it fails open rather than going silent. Switching channels while Isolate is on re-aims it.
  • 🎭 Scenes tab — design overlay scenes OBS-style. One picker: whichever scene is selected here is the live scene, the one the camera and every session overlay use. Pick a resolution, then drag overlays onto the canvas (◢ resizes, ⟳ rotates, Shift frees them from the 5% grid). The canvas previews at the virtual cam's actual resolution, so what you lay out is what viewers get.
    Overlay kinds: 🖼 Media (image or video, with chroma key for green-screen clips) · ▬ Solid (a flat colour block, full-frame by default — a backdrop with no image file) · 🅣 Text (multi-line, left/centre/right) · ⏳ Timer · 📊 Capacity Gauge · ⏱ Device Timers · 🗳 Poll Viewer (draws itself only while a poll runs) · 🔊 Audio (plays a sound on this machine; nothing is drawn on the stream).
    Each overlay is either always-on (part of the scene whenever it's live) or callable (played by an action, a button or a scene group — it ghosts on the canvas rather than vanishing, so you can still place it). Text placeholders keep updating while they're on screen, so Starting in [intro_timer]s or [var:score] ticks live without re-firing.
    Scene groups are named sets you fire and clear as one. The 👁 beside the group dropdown puts the group on or off the stream — an off group isn't on screen and doesn't come up when the scene loads, but firing it still plays it, which is how an on-demand group (fireworks, an outro) works. 🎬 flags a group as an intro (it only ever plays during the pre-show). ➕ 📋 ✏️ 🗑 create, duplicate, rename and delete groups; the scene itself has the same icons beside its name. A scene_group action can tick ⬆ on top to draw the whole group above everything already on screen.
    The 🗂 Media browser is the universal library — images, video and audio all live in data/images, so PC ↔ Android Config Sync and Export bundle them automatically.
  • The scene drives the feed: whichever scene is selected on the Scenes tab is the live one — its callable overlays appear as buttons in the 🎥 section, and ▶ Start virtual cam puts the always-on items (and live gauges) on the feed.
  • ⏱ Device Timers overlay — one row per configured device, primary pump always on top, each with its own countdown; rows appear as you add devices. Secondary pumps feed the same capacity gauge on their own calibration (rates add up — two pumps fill twice as fast). Row text uses [name] and [secs], and you can hide idle devices.
  • 🟩 Green-screen clips. Tick chroma key on any media overlay to knock its background colour out, so an ordinary .mp4 shot against a green screen plays over your camera with a transparent background — no alpha codec or WebM conversion needed. Pick the key colour (green by default, blue screens work too), tolerance for how much of that hue goes, and edge softness so hair and motion blur don't get a hard jagged cut. Greys and skin tones are protected, so shadows don't punch holes.
  • 🗳 Poll Viewer overlay — a resizable embed-style card that appears by itself while a poll is running (tick show while a poll runs), listing every option with a live vote bar and its own countdown. When the poll ends it switches to the results — winner highlighted — holds them for the number of seconds you set, then fades out. Each Poll Viewer keeps its own hold time, so two can differ.
  • 🔢 Variables — the var action stores a value you can read back anywhere with [var:name]. Pick session-wide (shared by everyone) or per player (read back as [uvar:name]), and set / inc / dec / mult / div it. Values accept arithmetic, so [var:pumps] * 50 works in any number field. Variables clear on session reset.
  • ❓ if / otherwise — branch on real data: each condition compares two sides (placeholders on either, numbers compared as numbers) with is / is not / > / < / ≥ / ≤ / contains / is empty, and you choose whether ALL or ANY must pass. Both arms are ordinary action blocks, so anything can go inside.
  • 🎲 random — pick ONE of several branches. Each branch takes an optional weight (leave them equal for an even split); [picked] and [picked_label] say which won.
  • 🏷 label / goto / goto_if / group — jump around inside a block instead of nesting deeper. Drop a label (or name a group), then goto it; goto_if jumps only when its conditions pass, which is how you build retry loops and skip-aheads. Jumping to a label resumes after it; jumping to a named group runs that group and then carries on. Jumps are capped at 2000 per block, and an unknown label is a quiet no-op.
  • 🛑 cancel — stops every other running action block (events mid-loop, waits, overlapping commands) while this one carries on. The panic button when things overlap.
  • "once" tickbox — on any action row. That row fires a single time per session and is skipped afterwards, resetting on session reset. Each command keeps its own memory, so the same row in two places doesn't share a count.
  • 🎬 Go Live Options (Scenes tab) — flipping LIVE on can open with an intro instead of starting the game. A scene group plays, an optional announcement posts (repeating and refreshing if you want), and commands stay held the whole time — anyone who tries gets a polite standby reply instead of pumping during your pre-show. Timed events wait too. You can allow specific commands through (a signup, say). Set a length, or set it to 0 and the intro waits until you press 🎬 Start now in the Chat tab — that button appears only while an intro is running and shows the countdown. Flipping LIVE off mid-intro cancels it cleanly. The camera sends black whenever the session isn't LIVE — so you can start it, pick it in Discord and get set up without anyone seeing the room — and it stays black through the intro (untick black during intro if you'd rather show the camera behind it). Overlays draw on top of the black either way. [intro_timer] counts down in messages and in Text overlays. The announcement can carry an image (picked from the media library), posted with the first message.
  • Turning a scene group off — the 👁 beside the group dropdown takes the whole group off the stream: it goes away immediately and doesn't come up when the scene loads. It is not a mute — firing it (a button, an event, a scene_group action) still plays it, which is exactly how an on-demand group like fireworks or an outro works: leave it off, fire it when you want it. Its overlays grey out on the canvas so you can still see where they sit. Click again to put it back on. Handy for building a group you aren't ready to use, or dropping a segment from a show without deleting it.
  • 🎬 Scene groups — there's no separate place to create one: on the Scenes tab, click an overlay and type a name into its Scene group box (say intro) — the group exists the moment an overlay carries that name, and the box autocompletes names you already use. Every group in the scene is listed under the canvas with its overlay count; click one to jump to it. Then scene_group plays the whole set at once and scene_group_kill clears it. Each overlay keeps its own mode, position and fades. Firing a group that has no overlays does nothing at all.
  • 🗂 Layer order — every overlay has a layer order number (with ⬆/⬇ buttons): higher draws on top. Equal numbers keep fire order, so the newest still lands above. The designer canvas stacks the same way it will on the feed.
  • 🔁 repeat — run a nested block a fixed number of times (the count can be a placeholder) or until conditions pass. [loop_i] is the round number. Loops are hard-capped at 500 rounds so a mistake can't wedge the bot.
  • Notification overlays that don't pile up. Two tickboxes on every overlay: animate & fade slides it in and out in a direction you pick (up/down/left/right, timed by its fade settings), and queue if busy makes a second fire wait its turn instead of replacing what's on screen. Together that's the OBS alert-box behaviour — if ten people trigger the same alert at once, they play one after another rather than landing on top of each other. Without queue, the newest simply replaces the current one (deep bursts past a dozen are dropped rather than queued forever).
  • ⏳ Timer overlay — a countdown with its own label. Idle it just shows its configured length; the start_timer / stop_timer actions run and freeze it (stop holds the remaining time, start resumes it, and start can override the duration). Tick auto start on load to begin the moment its stage goes live, and auto vanish on complete to have it remove itself at zero (with its fade-out). Use [secs] or [mmss] in the label for the number.
  • Placeholders in overlay text. Text and Timer labels accept the same [placeholders] as messages, and they carry over from whatever fired the overlay — so an overlay played by a command can show [user], [mention], [roll], [result] and the rest of that command's context. Those are filled in once, when the overlay appears. [capacity] and [secs] are the exception: they stay live and keep updating on screen.
  • Overlay actions call Stage overlays. You design an overlay once on the Stages tab; a command or event action just picks it from a dropdown and plays it — position, size and styling all come from the design. Choose timed (N seconds), static (stays until killed) or play once, with optional fade in / fade out. The overlay_kill action removes one the same way (with a fade if you want); killing an overlay that isn't currently up does nothing at all, so it's safe to use defensively.
  • Command pacing. Plug commands are paced per device — cloud vendors (Govee, Tuya, Wyze) at most one ON every 2s, LAN vendors every 0.5s — so a burst of events can't get you throttled or banned by a vendor's API. Turning a device OFF is never delayed, at any time: it's a safety operation and always goes straight through.
  • Renaming devices — the ✏️ next to any device on the Devices tab. Purely cosmetic: everything references devices by id, so renaming can't break commands, ranges or overlays. Leave it blank to restore the original vendor label.
  • 🖥 Take over the PC session (System tab, phone app). Hands the whole app over to your PC's DiscoFlate — every tab, not just Chat — so you drive the PC instance as if you were sitting at it, while the PC stays the bot and the camera home base. A 🖥 CONTROLLING PC · ↩ Release chip sits in the header the whole time; tap it (or the back button) to return to this phone's own instance. Needs Remote access enabled + this phone whitelisted on the PC. If both installs share a bot token, takeover offers to switch this device's Activation off first, so commands don't get answered twice.
  • 🔁 PC ↔ Android Config Sync (System tab) keeps both installs matching over Wi-Fi — all your scenes with the commands, events, buttons and wording each one owns, and the overlay images/videos they use. ⬇ Pull brings the other device's setup here; ⬆ Push sends this one's over — so a Stage built on the phone lands on the PC without export/import or walking over. 📡 Send scenes (beside them) pushes just your scenes and their media. Push asks the other device to fetch from this one, so Remote access must be on at both ends, each whitelisting the other's IP. Same-name-same-size files are skipped; tokens, devices and network settings never sync.
  • The permission line (under the send box) shows the bot's rights in the scoped channel live: 🚫 = it can't post there (Send disables, the missing permissions are listed) · ⚠ no Manage Webhooks = owner posts fall back to the bot-prefixed style · ⚠ no Read Message History = the mirror starts from now (no backfill).

Granting Manage Webhooks on a server the bot already joined

No re-invite needed — it goes live on the Chat tab's next refresh (a couple of seconds):
  • Server-wide: Discord → Server Settings → Roles → the bot's own managed role (named after the bot) → Permissions → enable Manage Webhooks → save.
  • One channel only (e.g. on someone else's server): right-click the channel → Edit Channel → Permissions → add the bot's role as an override → ✓ Manage Webhooks.
  • Fresh invites: the Discord tab offers two links — the full one (includes Manage Webhooks) and a webhook-free one for cautious admins; permissions are per-server, so use whichever fits each server.

Set up your private Discord bot
A 2-minute, one-time setup. There's no verification or app review — that only applies to bots in 100+ servers. Each person runs their own bot with their own token; never share a token.
  1. Open the Discord Developer Portal → New Application → give it a name (e.g. your bot's name) → Create.
  2. Left sidebar → Installation. Set Install Link to None — this removes the public add-to-server link. Do this first: Discord won't let you change the gateway intents (next steps) until Install Link is None. In that same tab, under Installation Contexts, make sure Guild Install is checked (User Install can stay off) — without it you'll get "Installation type not supported" when you try to add the bot to a server.
  3. Left sidebar → Bot, turn Public Bot OFF — now only you can invite it. This is what makes it a private bot.
  4. Still on the Bot page, under Privileged Gateway Intents, turn Message Content Intent ON (required so it can read commands) and Save.
  5. Get the token: on that same Bot page, in the Token section click Reset Token (Discord keeps the token hidden, so this reveals a fresh one) → Copy it immediately — it's only shown once. Keep it secret; it's your bot's password. You'll paste it into DiscoFlate's Discord tab shortly. (Lost it? Just Reset Token again — that makes a new one.)
  6. Left sidebar → OAuth2 → URL Generator. Tick scope bot; under permissions tick Send Messages (and Attach Files if you'll use images/snapshots). Copy the generated URL at the bottom, open it, and add the bot to your server.
  7. Back here → Discord tab → paste the token → Save & connect → pick the server and channel to listen on.
  8. Flip Activation on (top-right) and test from the Chat tab → Controls.
If it connects but doesn't respond to commands, re-check that Message Content Intent is on and that you picked the right channel.

Adding your bot to someone else's server

Because it's private, only you can add it — you can't hand a friend a link. Two ways to get it into a server you don't own:
  • Stay private (cleanest): have that server's owner give you the Manage Server permission there, then open your own invite link (step 6) and pick their server — as the app owner it works even while private. Remove the permission afterward if you like.
  • Temporarily go public: Portal → Bot → turn Public Bot ON, and Installation → set Install Link to Discord Provided Link. Now anyone with Manage Server there can add it with the link. Once it's in, switch Public Bot back OFF and Install Link back to None to re-lock it.
Either way it's harmless to be in another server — your bot only fires your devices and only listens in the channel you select; elsewhere it just sits idle.

Set up Tuya / Geeni / Smart Life plugs
Tuya-based plugs (incl. Geeni and anything in the Smart Life app) are controlled through Tuya's cloud API. The credentials come from Tuya's developer platform — not your Geeni/Smart Life app login. Tuya labels them with slashed double names, which is why they look unfamiliar: Access ID / Client ID and Access Secret / Client Secret.
  1. Go to platform.tuya.com ↗ and create a free developer account (separate from your plug app's login).
  2. Cloud → Development → Create Cloud Project. Pick the data center matching where your app account lives — US (Americas) for Geeni and most US plugs. It must match the Data center dropdown in Devices → Brand credentials, or every call fails with an auth error.
  3. The project's Overview tab shows Access ID/Client ID and Access Secret/Client Secret — paste those two into DiscoFlate → Devices → Tuya / Geeni credentials.
  4. Enable the IoT Core service on the project (Service API → free trial subscription). Without it, device calls fail even though the credentials are right.
  5. In the project: Devices → Link App Account → scan the QR with your app. ⚠️ Geeni gotcha: the QR link works with the Smart Life or Tuya apps, but usually not Geeni's own app. If your Geeni account won't link, re-pair the plugs into the Smart Life app (same hardware, same protocol) and link that.
  6. Your plugs now appear in the project's device list — each shows a Device ID. That's what goes in the device_id field when you add the plug in DiscoFlate → Devices. Select it as the active pump and Calibrate.
If a call fails after setup: check the data center matches the project, the IoT Core trial hasn't expired, and the device is linked into this project (not just visible in the phone app).

Set up ESPHome (for Kauf plugs)
Kauf plugs run ESPHome firmware with a built-in local web interface — that's what DiscoFlate talks to (no cloud, no account). Most stock Kauf plugs have it enabled out of the box.
  1. Get the plug on your Wi-Fi: on first power-up it broadcasts a setup hotspot (Kauf Plug XXXX) — connect to it, or use Kauf's captive-portal, and join it to your network.
  2. Find its IP address — check your router's device list, or try the hostname (e.g. http://kauf-plug.local).
  3. Confirm the web server is on: open http://<plug-ip> in a browser. If you see a page listing switches/sensors, you're good. If the browser says the connection was refused, the plug has no web server running — the ESPHome web_server: component is off by default. Add it to the plug's ESPHome config and re-flash, then retry. (A "connection refused" in DiscoFlate's Activity log means the same thing.)
  4. Note the switch id from that page — it's usually relay (DiscoFlate's default). If yours is named differently, remember it.
  5. In DiscoFlate → Devices → Brand = Kauf → enter the plug's host (its IP) and, if it isn't relay, the entity (switch id). Click Add.
  6. Select it as the active pump (radio) and Calibrate it (run it, tap Full when done) so capacity tracks.
  7. Only if you enabled web-server auth on the plug: fill the Kauf credentials (web username/password) in the collapsible section above the device list.
If the plug won't respond, open http://<plug-ip> directly and try toggling the switch there — that confirms the web server is reachable and gives you the exact switch id.

Troubleshooting

"Connection refused" / plug won't respond
Connection refused (in the Activity log, or in a browser at http://<plug-ip>) means nothing is serving HTTP at that address+port — it's not a wrong switch id (that gives a 404) and not the plug being offline (that times out). The plug answered and said "no listener here." Work through these in order:
  1. Right IP? Confirm 192.168.x.x is actually the plug (router device list / http://kauf-plug.local). A refusal from the wrong device looks identical.
  2. Different port? Some builds put the web server on :8080. Try http://<plug-ip>:8080 in a browser — if that loads, just enter <plug-ip>:8080 as the host in Devices. No re-flash needed.
  3. No web server at all? If neither port loads, the ESPHome web_server: component isn't running (it's off by default in ESPHome). Add it to the plug's config and re-flash — see "Where is the ESPHome YAML?" below.
Add this to the device's YAML, then Install/flash (OTA — no USB needed since it's already on ESPHome):
web_server:
  port: 80
Where is the ESPHome YAML?
Depends on how the plug was set up:
  1. Home Assistant + the ESPHome add-on (most common) — files live on the HA host at /config/esphome/<device-name>.yaml. Easiest: ESPHome dashboard → the device's card → EDIT. Or open the file via the File editor / Samba / SSH add-on. Shared secrets are in /config/esphome/secrets.yaml.
  2. Standalone ESPHome (Docker, or pip install esphome on a PC) — the .yaml files sit in whatever directory you run esphome from, typically ~/esphome/ or a mounted config/ dir. One <name>.yaml per device plus a shared secrets.yaml.
  3. Flashed from the web installer (web.esphome.io) with no dashboard — there's no persistent YAML file; config only exists at flash time. Re-create it in a dashboard (option 1 or 2) to change anything.
Kauf plugs specifically: Kauf ships adoptable stock firmware. In the ESPHome dashboard the plug appears via mDNS with an ADOPT / TAKE CONTROL button — adopting it generates a small local <name>.yaml in /config/esphome/ that references Kauf's published package (github.com/KaufHA). That generated file is where you add web_server:, then Install.
Flashing / enabling web_server (web & OTA)
If the plug is already on ESPHome and your Wi-Fi (it is, if you set it up before), you almost never need a USB cable — do it over the air. USB web-flashing is a last resort, and a Kauf mains plug has no external USB port, so it means opening the case.

Route 1 — OTA via the standalone ESPHome dashboard (no cable)

Set up the dashboard (either one runs as a local web app in your browser):
pip (Python 3.9+; a venv is cleanest):
pip install esphome
esphome dashboard config/
Serves the dashboard at http://localhost:6052, storing each device's YAML in config/. Or Docker (same LAN as the plug):
docker run --rm --net=host -v "$PWD/config:/config" -it ghcr.io/esphome/esphome
Then flash it OTA:
  1. Open http://localhost:6052. The plug appears under Discovered (via mDNS) since it's already on ESPHome + your Wi-Fi.
  2. Click ADOPT / TAKE CONTROL → name it → the dashboard writes config/<name>.yaml (referencing Kauf's package).
  3. Open that device's ⋮ → Edit (or edit config/<name>.yaml) and add web_server: { port: 80 } (as two lines).
  4. Save → Install → Wirelessly (OTA). It compiles and pushes over Wi-Fi — no cable. (First compile downloads the toolchain and is slow; later ones are quick.)
  5. After the plug reboots, http://<plug-ip> loads → add it in DiscoFlate → Devices.
⚠️ Run the dashboard on the same network as the plug or mDNS/OTA won't reach it. Kauf stock firmware may prompt for an OTA password during install — default documented on github.com/KaufHA.

Route 2 — USB web-flash via web.esphome.io (only if OTA is impossible)

Needs a Chromium browser (Chrome/Edge — WebSerial isn't in Firefox/Safari), a 3.3 V USB-to-UART adapter, and access to the ESP's pads. ⚠️ A Kauf mains plug has no external USB — you must open the case and wire an adapter with the plug unplugged from mains. Advanced; use Route 1 if you're not comfortable.
  1. Plug unplugged from mains. Open it; wire USB-UART: TX↔RX, RX↔TX, GND↔GND, 3V3↔3V3. Pull GPIO0 low / hold the button to enter flash mode.
  2. Open https://web.esphome.io in Chrome/Edge → Connect → pick the serial port.
  3. Either Prepare for first use (installs base ESPHome, then adopt it in the dashboard and add web_server: as in Route 1), or Install a .bin you exported from the dashboard that already includes web_server.
Kauf shortcut: Kauf ships a browser-based installer (ESP Web Tools) and their latest stock firmware already has web_server enabled. Flashing current Kauf firmware — via their web updater or OTA — re-enables it without hand-editing YAML. See kaufha.com / github.com/KaufHA for current steps.

Any of these can go in any message field; they're filled in when the bot posts.
Conditional lines: start a line with [if name] and it shows only when that placeholder has a value — e.g. [if runnerup]🥈 Runner-up: [runnerup] only appears when there was a runner-up. Use [if not name] for the opposite. Works with any placeholder below, on a per-line basis (soft word-wrap doesn't count — only real line breaks).

[mention]@pings the person (a real Discord mention)

Formatting

Press Enter for a new line. Discord markdown works: **bold**, *italic*, `code`. A literal \n also becomes a newline.

Readability — Display output headers

When several people fire commands and multi-stage minigames at once, the lines braid together. Turn on Display output headers (Game → Limits & announcements, at the top) and every command / minigame / event message is prefixed with a **[label · user]** tag, so each line is traceable to who and what it belongs to. The user portion respects cross-server anonymity — servers where the actor isn't a member see ANON instead of the name.
Turn on Rich status embeds (same spot) to post the capacity check, both leaderboards, the auto-report, and custom Broadcasts as bordered embed cards instead of plain text — the border and color stripe make those status blocks stand apart from rapid command chatter. Per-command replies stay plain (use react only or Display output headers for those).

Minigames — how each one plays
Minigames are custom command types (Commands tab → Type → game-*). Running one posts a public ▶ Play button locked to whoever typed it; the game itself is ephemeral (only the player sees it), and when it ends the tiered result broadcasts to the channel — with any pump fires credited to the player's leaderboard. Slots is the exception: it plays fully in-channel with no Play button. Every game maps its final score through your Outcome tiers (score → message + optional device fires), so YOU decide what a win pays. A per-range or Always-On Luck value is a flat ± added to the score before the tier is picked.

💨 Push Your Luck (game-pushluck)

Press-your-luck banking. Each 💨 Pump adds Points/pump to a pot — but the bust chance starts at Bust start % and climbs +% / pump with every press. 🏦 Bank locks the pot in as the score; busting scores 0. Hitting Max pumps auto-banks. Score = points banked. Tune it greedy (low start, steep step) or generous (high ceiling, shallow step).

🧠 Simon (game-simon)

Memory. The bot shows a growing emoji sequence for Reveal (s) seconds, hides it, and the player repeats it with buttons. Each cleared round adds one symbol. One wrong press ends the game. Score = rounds fully cleared; clearing Max rounds is a perfect run. Fewer Symbols (2–6) and a longer reveal = easier.

🎈 Don't Pop It (game-balloon)

Minesweeper-style nerve test. A grid of Cells hides Balloons; revealing a safe cell adds Points/cell, and 🏦 Cash Out keeps the total. Revealing a balloon pops — score 0. Clearing every safe cell scores the whole board. Score = points held at the end. More balloons per cell = spicier.

✊✋✌️ Rock Paper Scissors (game-rps)

Best-of series vs the bot — first to Rounds to win takes the match, ties replay. Score = rounds the player won (win or lose the match), so tiers can pay partial credit for a close loss or reserve the top tier for a sweep.

🎰 Slots (game-slots)

One public pull — the reels spin right in the channel. Score is fixed: 3 = three of a kind, 1 = any pair, 0 = no match. Symbols (2–8) sets the odds: more symbols = rarer wins (with 6 symbols a triple is 1-in-36, a pair about 42%). Tiers at ≥3 / ≥1 / ≥0 map jackpot / small win / nothing.

🃏 Blackjack (game-blackjack)

Classic 21 vs the dealer, infinite deck, Hit / Stand, dealer stands on 17. Score is fixed: 0 = bust or dealer wins · 1 = push (including blackjack-vs-blackjack) · 2 = win · 3 = natural blackjack on the deal. No knobs beyond the tiers — the game IS the odds.
Shared rules: a game charges its cooldown + per-person use when the command runs (not when Play is pressed); one use = one game. Abandoned games pay nothing. A session pause cancels live games and refunds the use. Results are labelled with the game's name and respect cross-server anonymity. Placeholders [score], [luck], [secs], [secs2capacity], [game] work in tier messages, and games can trigger Starts events on completion.
